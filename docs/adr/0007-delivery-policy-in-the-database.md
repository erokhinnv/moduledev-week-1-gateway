# ADR 0007. Политика доставки принадлежит базе, а `DEAD` остаётся техническим исходом

- Статус: принято
- Дата: 2026-09-30
- Контекст недели: 4 (надёжность и восстановление)

## Контекст

Неделя 4 ставит рядом двух dispatcher из одного образа и требует ограниченного retry с
экспоненциальной задержкой и jitter, перехвата просроченной доставки и наблюдаемого исчерпания
попыток. При этом контрольные значения профиля (`4` попытки, `200/400/800` мс, jitter `0..100` мс,
аренда `2` с) задаются проверкой через переменные окружения, а не выбираются решением.

Неделя 3 хранила профиль в строке `delivery.delivery_policy` с «лестницей задержек» `delays_ms`, и
контур не мог изменить его иначе как миграцией. Это ломает сразу два требования: значения должны
приходить конфигурацией, и они должны действовать для ОБОИХ dispatcher одинаково.

Второй вопрос недели — что означает исчерпание попыток. Provider мог принять платёж и потерять
ответ. Если `DEAD` доставки перевести в отказ операции, платформа объявит ложный предметный
результат по техническому признаку.

## Решение

### Профиль — настройка базы, а не константа и не параметр клиента

`db/init/00-roles.sh` получает значения профиля переменными окружения сервиса `postgres` и
превращает их в настройки самой базы:

```sql
ALTER DATABASE course SET course.outbox_max_attempts    = '4';
ALTER DATABASE course SET course.outbox_backoff_base_ms = '200';
ALTER DATABASE course SET course.outbox_backoff_max_ms  = '800';
ALTER DATABASE course SET course.outbox_jitter_max_ms   = '100';
ALTER DATABASE course SET course.outbox_lease_ms        = '2000';
ALTER DATABASE course SET course.job_lease_ms           = '2000';
```

`delivery.active_policy()` читает их через `api.setting_int(name, fallback)` и откатывается к
строке `delivery.delivery_policy` профиля `default`/`test`, если настройки нет — например на томе,
созданном до этой миграции. Значения ограничиваются сверху и снизу внутри функции: опечатка в
окружении контейнера не имеет права ни остановить доставку навсегда, ни сделать аренду бесконечной.

Почему настройка базы, а не таблица, заполняемая CLI. Профиль обязан действовать одинаково для
обоих dispatcher, а решают они ничего: и `claim_outbox`, и `fail_outbox` — функции PostgreSQL.
Клиент при этом не может подменить профиль своим параметром: `current_setting` читает значение
уровня базы, а не сессии клиента, и ни одна граница не принимает его аргументом.

`workflow.claim_jobs` получает то же самое для срока аренды задания: не переданный `p_lease_ms`
заполняется `course.job_lease_ms`. Worker по-прежнему передаёт значение явно, поэтому настройка
базы — это ДЕФОЛТ контура, а не второе мнение о том же числе.

### Экспонента с jitter вместо лестницы задержек

`delivery.backoff_ms(attempt, policy)` считает
`least(base * 2^(attempt-1), max) + random(0..jitter)`. При базе 200 мс и потолке 800 мс это даёт
200, 400, 800 мс — те же значения, что раньше лежали списком, но теперь как правило, а не как
таблица. Список `delays_ms` больше не участвует в решении: два несогласуемых источника одной
политики рано или поздно расходятся.

Jitter добавляется всегда, а не только при совпадении моментов. Два dispatcher, получившие отказ в
одну миллисекунду, обязаны разойтись во времени сами, без внешнего координатора.

### Бюджет попытки включает разрешение имени

`COURSE_PROVIDER_TIMEOUT_MS` — бюджет ВСЕЙ попытки, а не только сокета. Это не придирка к
формулировке: socket timeout покрывает connect и read, но `getaddrinfo` не покрывает вообще. На
этом Docker-host отсутствующее имя `provider-simulator` стоит **8 секунд** при объявленном бюджете
500 мс — измерено, а не предположено.

Последствие серьёзнее, чем «медленно». Попытка, живущая 8 секунд, переживает двухсекундную аренду
доставки: к моменту отчёта доставку уже перезахватил другой dispatcher, отчёт отклоняется fencing'ом
(`delivery.lease_stale`), и попытка потрачена дважды — на ожидание и на отказ. Снаружи это выглядит
как застрявшая доставка, которой нет объяснения ни в одном сохранённом факте.

Поэтому попытка выполняется на daemon-потоке и БРОСАЕТСЯ по истечении бюджета
(`provider._within_budget`). Брошенная попытка может всё же дойти до provider — и это допустимо:
стабильный `externalRequestId` оставляет один платёж, а её результат всё равно игнорируется, потому
что отчёт условен по owner и версии аренды. Цена решения — поток, который живёт до собственного
завершения; он daemon, поэтому остановку процесса не задерживает.

### `DEAD` — исход доставки, а не операции

Исчерпание попыток фиксируется только в Outbox: `state = DEAD`, непустые `dead_at` и
`last_error_code`, сохранённый `attempt_count`. Операция остаётся `PROCESSING`, процесс — в
`WAITING_SIGNAL`. Отдельного флага ошибки у процесса нет: вопрос «дошёл ли запрос» и вопрос «каков
предметный результат» — разные вопросы, и ответ на первый не является ответом на второй.

Поздняя валидная квитанция имеет приоритет: `payment.receipt_accept_v1` переводит доставку
`DEAD → CONFIRMED` и продолжает процесс. `dead_at` при этом НЕ стирается — триггер `outbox_guard`
объявляет его write-once наравне с `delivered_at` и `confirmed_at`. Диагностика исчерпанной
доставки обязана пережить её подтверждение: иначе разбор «почему платёж шёл сорок секунд» терял бы
единственное свидетельство.

Операции, застрявшие в этом состоянии, ищет действие `diagnostics.stalled`: Outbox `DEAD` при
операции `PROCESSING`. Признак «затянулось» — сохранённый факт, а не таймер наблюдателя.

## Последствия

- Профиль меняется конфигурацией контура без миграции и без пересборки образов.
- Значения приходят в PostgreSQL один раз при инициализации тома. На уже инициализированном томе
  `ALTER DATABASE` не выполняется повторно, поэтому смена профиля требует пересоздания тома либо
  ручного `ALTER DATABASE` — это написано в README, потому что иначе выглядит как «настройка не
  применилась».
- Два dispatcher не нуждаются ни в каком согласовании между собой: конкуренцию разбирает
  `SKIP LOCKED`, а право на отчёт — пара «владелец + версия аренды».
- `DEAD` требует операционного решения, а не автоматического отказа. Платформа его не принимает —
  она только делает состояние наблюдаемым.
