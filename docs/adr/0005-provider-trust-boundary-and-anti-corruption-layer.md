# ADR 0005. Граница доверия provider и Python anti-corruption layer

- Статус: принято
- Дата: 2026-09-14
- Контекст недели: 3 (Python-периметр)

## Контекст

Внешний provider v0.2.0 — выданный Go-компонент с legacy wire contract вступительного задания:

- `POST /payments` принимает `operationId`, который обязан совпадать с `Idempotency-Key`;
- callback приходит без JWT и без HMAC, в собственной форме: `providerPaymentId`, `operationId`,
  `result`, `message`, `occurredAt`.

Внутренний контракт платформы — версионированная квитанция receipt v1, которая попадает в
generic C# API через обычный маршрут `POST /api/receipt/accept`. Нужно одновременно:

1. не пустить legacy-формат внутрь предметной модели;
2. не дать никому, кроме нашего периметра, изменить состояние по квитанции;
3. не завести в C# отдельный controller или ветку «для квитанций»;
4. не хранить авторитетное состояние вне PostgreSQL.

Два соблазнительных решения отвергнуты.

**Принимать legacy callback прямо в C# API.** Тогда формат внешней системы становится частью
generic runtime: появляется action-specific разбор, а смена provider ломает ядро.

**Подписывать уже разобранный объект на принимающей стороне.** Если API пересериализует JSON и
считает HMAC над результатом, подпись доказывает только то, что сериализаторы совпали. Любой
посредник, изменивший пробелы или порядок ключей, «сохранит» подпись, а два байтово разных тела
получат один отпечаток в Inbox.

## Решение

### Anti-corruption layer — отдельный Python-процесс `receipt-adapter`

Adapter слушает единственный маршрут `POST /callbacks/provider-v02/{capability}` внутри сети
Compose и:

- сравнивает capability за постоянное время; неверный путь — `404` с пустым телом;
- строго валидирует тело: UTF-8, JSON-объект без дублирующихся ключей и `NaN`, ровно пять полей,
  типы и длины, запрет CR/LF, `occurredAt` — RFC 3339 в UTC; иначе `400` с пустым телом;
- переводит callback в receipt v1: `messageId = providerPaymentId`,
  `externalRequestId = operationId`, `outcome = result`, исходная строка `occurredAt`;
  `message` проверяется и отбрасывается;
- сериализует квитанцию как compact JSON с sorted keys (`ensure_ascii=False`, без BOM и LF);
- считает `X-Provider-Signature: v1=<hex HMAC-SHA256>` над ЭТИМИ байтами с ключом — точными
  UTF-8 байтами `PROVIDER_HMAC_SECRET`;
- отправляет те же байты через gateway с JWT `receipt-provider` (`receipt:write`),
  `Idempotency-Key = messageId`, `X-Action-Version: 1`;
- возвращает provider статус, тело и media type ответа API; при недоступности API — `503`
  `dependency.unavailable`. Сам adapter повторов не делает: у provider собственная политика.

`messageId = providerPaymentId` делает повторный и конфликтующий callback одного платежа одной
областью дедупликации: identical body — тот же результат, другой body — `409`.

У adapter нет учётных данных PostgreSQL (проверяется и по Compose, и по отсутствию переменных),
поэтому его компрометация не даёт ни чтения, ни записи состояния в обход generic API.

### Generic signature boundary в C# API

`api` проверяет подпись над точными байтами тела до разбора JSON и до разрешения action. Граница
не знает, какому действию подпись нужна:

| Ситуация | Результат |
|---|---|
| Заголовка нет | запрос идёт дальше без маркера |
| Формат, версия, регистр hex или HMAC неверны; несколько заголовков | `401 signature.invalid`, target не вызывается |
| Подпись верна | в server-side context появляется `transport: {signatureVerified: true, signatureVersion: 1}` |

Секрет и полученная подпись не попадают ни в context, ни в журнал. Сравнение — декодированных
байт через `CryptographicOperations.FixedTimeEquals`. Отпечаток точных байт тела передаётся в
context как `payloadHash` для всех запросов: jsonb-представление payload байты не сохраняет, а
Inbox обязан хранить SHA-256 именно того, что было подписано.

Требовать маркер — дело зарегистрированной функции. `payment.receipt_accept_v1` без него
возвращает `receipt.signature_required`; матрица кодов отображает его в `403`. Новое подписанное
действие появится публикацией манифеста и функции — без правки C#.

### Что доказывает HMAC и чего не доказывает

HMAC защищает участок **adapter → platform**: квитанцию может создать только держатель секрета,
и изменение любого байта ломает подпись. Provider v0.2.0 сам ничего не подписывает, поэтому
доверие к его callback в учебном контуре ограничено изолированной сетью Compose и
непредсказуемым capability-сегментом. Это не модель банковского криптографического периметра:
в production на месте capability был бы mTLS или подпись самого provider.

### Слои, которые выбор flow и статус не видят

Python не выбирает flow, лимит, переход или финальный статус. Adapter лишь переводит формат;
квитанция сохраняется в Inbox, а исход операции применяет workflow-шаг `payment.apply_receipt`,
который читает только сохранённую и применённую квитанцию.

## Последствия

- Смена provider — новый adapter и, возможно, новая версия receipt; ядро и worker не меняются.
- Adapter строже receipt-schema в одном месте: `providerPaymentId` должен быть header-safe ASCII,
  потому что он же — `Idempotency-Key`. Такой callback получает `400` до API.
- `X-Provider-Signature` пропускается gateway прозрачно; gateway тело не читает и не журналирует.
- Подпись над точными байтами означает, что любой посредник, меняющий тело, будет отвергнут. Это
  намеренно: gateway пересылает тело потоком без изменений.
