# ADR 0002. Технический результат и предметный результат разделены

- Статус: принято
- Дата: 2026-08-23
- Контекст недели: 1

## Контекст

Один вызов action имеет два независимых исхода.

- **Технический**: запрос дошёл, аутентифицирован, разрешён в версию каталога, уложился в
  deadline, транзакция зафиксирована или откачена.
- **Предметный**: зарегистрированная функция приняла решение — создала operation, нашла её,
  отказала по бизнес-правилу.

Смешение этих исходов даёт две типичные ошибки: предметный отказ отвечает `500`, а технический
сбой выглядит как успешный ответ с пустым результатом.

## Решение

1. Зарегистрированная функция возвращает единый envelope со `status` `ok` или `error`. Успех
   обязан нести объявленный `outcome` и `result`, отказ — предметный `code`.
2. `api.invoke` не превращает предметный отказ в исключение. Он валидирует форму envelope,
   проверяет `outcome` по манифесту и возвращает результат вызывающему C#-слою. Исключение
   внутри target перехватывается в подтранзакции и превращается в контролируемый
   `internal.error` без SQL-деталей.
3. Технический слой принимает решение о фиксации **после** проверки контракта: `outcome` должен
   входить в `outcomes` манифеста, а `result` — проходить `response_schema`. Только затем
   выполняется `COMMIT`.
4. Любой не-`ok` результат откатывает всю транзакцию целиком. Предметный эффект, запись
   идемпотентности и история исчезают вместе: успешный idempotency-результат не сохраняется,
   если контракт нарушен.
5. Коды разведены по HTTP-матрице:

   | Исход | HTTP | `code` |
   |---|---:|---|
   | Объявленный outcome, валидный result | 200 | — |
   | Неизвестный outcome или невалидный result | 500 | `action.contract_violation` |
   | Предметный отказ зарегистрированной функции | 422 | код функции, например `operation.not_found` |
   | Недоступность PostgreSQL | 503 | `dependency.unavailable` |
   | Истёк deadline из `timeout_ms` | 504 | `action.timeout` |

6. Технический след переживает откат. `api.record_dispatch` вызывается на отдельном соединении
   вне предметной транзакции, поэтому в `autocheck.action_dispatches` остаётся запись
   `status = 'ERROR'` даже тогда, когда предметный эффект полностью откачен. Полный payload не
   публикуется — только его SHA-256.

## Последствия

- Предметная ошибка наблюдаема клиентом как контролируемый envelope и никогда не выглядит как
  сбой сервиса.
- Нарушение контракта разработчиком функции обнаруживается до фиксации, а не после.
- Dispatch и предметное состояние могут расходиться намеренно: dispatch — это журнал попыток,
  `operations` и `operation_events` — авторитетное состояние.

## Альтернативы

- **Предметный отказ через `RAISE EXCEPTION`.** Отклонено: исключение обрывает транзакцию,
  теряет envelope и вынуждает разбирать текст ошибки, который не должен покидать границу.
- **Предметный отказ с HTTP 200 и `status = error`.** Отклонено: нормативная матрица требует
  контролируемого error-ответа со статусом ≥ 400.
- **Запись dispatch внутри той же транзакции.** Отклонено: тогда техническая ошибка отката
  исчезала бы вместе с предметным эффектом, и причина отката была бы ненаблюдаема.
